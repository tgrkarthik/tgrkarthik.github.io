Writing Skills.md — My Learnings on Self-Improving Code

June 2026 • Skills & Architecture
TL;DR

Over three months I went from never having written several skills, to writing over a dozen, primarily for my professional work in finance, but also some routine day to day automation workflows. Each skills typically does something distinct, and the interesting evolution was that I kept relying on the model less and building more deterministic scaffolding around it. This is the field guide to what held up: provenance tags on every fact, a closed list of sources nothing may be cited outside of, web search as a switch rather than a default, failure logs read before every run, and gates written in plain Python that block delivery when something’s wrong.

I’ve written about a dozen skills for Claude since March.The mental model I landed on is that Claude is a fast, fallible analyst. Quick, broadly capable, reads anything you put in front of it, and will hand you a confident wrong answer wearing the same face it uses for a right one. Almost everything I’ve built since is a mechanism for catching that wrong answer before it ships. This is a companion to the toolkit piece I wrote earlier; that one is the what, this one is the how and the why.

Here’s the shape of it, oldest to newest.

March

Business-Understanding. Reads a company’s filings (10-Ks, S-1s, annual reports across the US, India and Europe) and pulls out what it does, how it earns, who its customers and rivals are. It taught me document triage: rank the filings before reading, and start with the Business Description section, because that one section gives you 70% of what you need.

April

Initiation Merge. A pure-Python script, no model involved, that stitches separate report stages into one document. The first step I deliberately took away from the model — because assembling text turned out to be a code problem, and model improvisation at the join is a defect, not a flourish.

April

Earnings Sentiment, and the first pipeline skills. Earnings Sentiment reads up to 16 quarters of earnings-call transcripts and pulls the recurring positives and concerns from management and analysts. This is where I started tagging every claim with where it came from, and where I split “closed-book” and “open-book” into separate skills.

April

SellSideInitiation. The flagship. One trigger phrase runs a five-phase pipeline that turns documents I supply into a 25-page closed-book research report. Eight hard rules, a six-tier source hierarchy, gates that block delivery. The most defended thing I’ve built.

April

investment-moats. Competitive-advantage analysis through four named frameworks — Helmer’s 7 Powers, Greenwald’s Earnings Power Value, Buffett-Munger, Porter. It proved the structure wasn’t tied to reports; the same discipline carried straight over to a framework skill.

April

voice-dna. How I write, across four formats and a professionalism dial, built from 16 of my own writing samples over seven years. It pointed the gate idea at prose instead of numbers.

May

user-profile. My standing instructions (identity, file paths, formatting standards, code conventions), loaded at the start of every task so nothing gets re-asked.

May – June

The personal-workflow trio. Lighter skills for my own notes: YouTube summaries into Obsidian, investor-call transcripts into filed and backlinked notes, years of conversation notes rolled into a cross-referenced workbook. Same discipline, lighter weight, faster model.

The arc, in five moves: a single-purpose framework, then a guardrail-heavy pipeline, then enforcement moved into code, then identity and voice, then repeatable personal workflows. What changes across it isn’t the subject. It’s how much of the work I trust the model to do unsupervised, which steadily shrinks, against how much deterministic scaffolding I build around it, which steadily grows.

Closed-book by default

The first thing I got wrong was treating the model’s own knowledge as a resource. It isn’t. A model knows a great deal about most public companies from training, and that knowledge is invisible, unverifiable, and often a year or two stale. So the rule across every analytical skill became blunt: training data is not a source. If I can’t point to a specific document I retrieved for a claim, the claim either gets tagged as unverified or doesn’t get made.

Making that real took three mechanisms. The first is provenance as a type. Every number in a report carries a tag from a fixed, six-symbol vocabulary saying where it came from: the data feed, a filing in the project folder, an official exchange filing, a transcript, a live web lookup, or — honestly — not retrieved. The tags are ranked, so the skill knows to drop to a weaker source only when the stronger one is empty. And because the vocabulary is closed, a script downstream can check that nothing slipped through untagged.

The second is an explicit, finite list of sources. Each report builds a log of every document it actually retrieved, and that log is the world. Nothing may be cited outside it, even if the model happens to know the contents. This is the sharpest idea I found in three months, because “don’t hallucinate” is not an instruction a model can follow — it has no internal flag separating a retrieved fact from a confidently recalled one. “Don’t cite anything outside this list” is a set-membership test, and a hundred lines of Python can enforce it.

The third is treating web search as a switch, not a default. In the report pipeline it’s off for the first three phases and turns on in exactly two named places: one step to fetch live market data, every cell tagged accordingly, and the valuation phase for prices and comparables. Everywhere else, off. Once the model can reach the open web mid-analysis, the whole provenance system leaks, because a number can enter whose source is just “something I found.”

The reframe underneath all three is the one that took longest to accept emotionally: a report with honest gaps is correct output, and a report with a confident wrong number is broken — even if the number happens to be right, because the process that produced it can’t tell the difference. An empty cell labelled “not retrieved” is a success. The model is so good at producing the plausible thing, and the plausible thing is usually close. Close is the whole problem.

The Snowflake run

For a while I parallelised the long pipelines with sub-agents — a merge agent, an audit agent, a data-extraction agent. Clean architecture, narrow briefs. Then I checked the numbers on one run carefully.

One section had come back with 100 of its 122 financial data points fabricated, by a sub-agent that had been given a perfectly clear instruction. Revenue and gross profit were right, because they were the first two fields in the API response. Everything after that was invented, with the correct source tags attached. The report read fine. It was wrong in nearly every detail.

The cause is architectural, not a bug. A sub-agent launches fresh. It can’t see my instructions file, the failure log, or the conversation. So when it hits a gap it has nothing to fall back on except training data, and it fills the gap plausibly. The orchestrator then stitches plausible-but-wrong fragments together with no way to see the seams, because each fragment is internally well-formed. So the rule now is absolute: no sub-agents for analytical work. Everything runs in one conversation with full context carried forward. It’s slower. It’s the only architecture I’ve found that delivers what it claims.

The failure log

Every serious skill has a file called FAILURE_LOG.md sitting next to it. It’s append-only. Each entry records what broke, the run that triggered it, and the rule that now prevents it. Reading it is step one of every run, before any retrieval or writing.

It works because it closes the loop between “something broke” and “the skill changed.” Without a log, every fix is local — this report, this company, this bug — and the same mistake comes back the following week in slightly different clothes. With a log, every fix is structural: a rule in the skill, a check in a gate, a line in the instructions file. New failures get written down in the same session they happen, never deferred, because by next time the context is gone. Trace almost any rule I have back far enough and you find a logged failure at the root of it. The Snowflake run is one. A run where a bank’s accounts got read with a software template, producing phantom debt that didn’t exist, is another. The log is the thing the skills actually grew out of.

The skill is the spec; the gate is the gate

A skill file is a prompt, and a prompt is a suggestion. The model follows it most of the time and quietly ignores it some of the time, and you don’t get told which run is which. For the rules that genuinely can’t bend, the only honest enforcement is code that fails the build.

So the rules I refuse to ship without are each backed by a small Python program that runs over the output and exits with an error when something’s wrong. One runs regex over prose and hard-fails on the worst machine-writing tells. One runs five checks over a finished report: no leftover placeholder tags, no unretrieved numbers in historical columns, citations that actually resolve, a balance sheet that reconciles to the dollar. One diffs the written numbers against the raw data feed to catch exactly the Snowflake failure. Each gate is a hundred lines or less, runs in seconds, and uses no model at all. That last part is the point: you can’t ask the thing that makes the mistake to also be the thing that reliably catches it. The catcher has to be dumber, deterministic, and incorruptible.

This is the same line drawn over and over. The model does judgment — reading, weighing, classifying, composing. Deterministic code does assembly, transformation, and checking. If a task has one correct output given its input, it belongs in code; if it needs reading and weighing, it belongs to the model, and its output then goes straight to code for assembly and verification. Most of my failures came from putting the model on the wrong side of that line: asking it to do bookkeeping and watching it improvise.

The smaller habits that compounded

A few lighter patterns earned their place. Classify the input before you process it. The report pipeline decides whether a company is a software business, a bank, an insurer, a REIT, a marketplace, a miner, or a holding company before it touches the financials, because each needs a different template and the wrong one corrupts everything quietly. That step exists because a bank once got read as a software company and the output looked clean while being conceptually wrong.

Tell the model where it may and may not exercise judgment. In my note-taking skills the body of a note is copied verbatim — no summarising, no improving — and the only authored parts are the title and a few lines of metadata. The model’s instinct is to add value everywhere, and “value” often means paraphrase, which is destructive when the whole point is fidelity to the source.

Write the skill against the tool, not the vendor. The data source appears throughout as a single named parameter with a note that today it’s one provider and tomorrow it might be another. Connectors change; a skill with the vendor’s name welded into forty instructions becomes a rewrite, while a parameterised one is a one-line change. Pick the model deliberately — the faster one for mechanical work, the stronger one for judgment — and ask your questions in one batch up front, never one a time, and never a question whose answer is already sitting in what I just told it.

The whole kit, on one page

Strip the finance out and twelve patterns are left. Each one survives the domain: substitute your own work for mine and it still holds. Here they are in one place, for the reader who wants the checklist rather than the story.

01
Provenance as a type
Tag every fact with where it came from, from a fixed, ranked, machine-checkable vocabulary. Design the tags before the output.
02
An explicit closed boundary
Build one finite list of retrieved sources. Nothing may be cited outside it, even what the model thinks it knows.
03
Web search as a switch
Off by default. Turned on only at named steps, for named fields, with its own source tag. Never ambient.
04
Training data is not a source
If you can’t point to a retrieved document for a claim, it gets tagged unverified or isn’t made. Honest gaps are correct output.
05
No sub-agents for judgment
Fresh agents lose context and fill the gaps from training. Run analytical work in one conversation, full context carried forward.
06
Failure logs, read first
An append-only record of what broke and the rule that now prevents it. Reading it is step one of every run; codify failures the same session.
07
The spec and the gate
A prompt is a suggestion. Non-negotiable rules get enforced by small Python programs that fail the build, not by careful wording.
08
The determinism boundary
The model does judgment. Deterministic code does assembly, transformation, and checking. One correct output given the input means it belongs in code.
09
Parameterise the tools
Write against a named source parameter, not a vendor. Connectors change; a skill with the vendor welded in becomes a rewrite.
10
Branch on input type early
Classify the input before processing it. The wrong template produces a clean, professional, completely wrong artifact.
11
Verbatim zones vs authored zones
Tell the model exactly where to copy faithfully and where to compose freely. It edits by instinct, which is destructive in a copy zone.
12
Model and question discipline
Pick the model deliberately, faster for mechanical work and stronger for judgment. Batch questions up front; never ask what you were already told.

Where this leaves me

The failure logs keep growing. The one next to the report pipeline is past two dozen entries, and each is a mistake the model made once and a line that now makes sure it can’t make it the same way twice. Every skill I write now opens the same way: read the log, confirm the parameters, decide what the model is and isn’t allowed to touch, and only then start.

It’s slower than just asking. It is also the only version I’d put my name on a report from. I don’t know what the next skill will break, or which rule it’ll add to the pile. I know it’ll start by reading the log.
